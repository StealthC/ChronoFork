# Execution Modes, Pacing and Headless Capture Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement `Unpaced`/`Paced`/`Manual` execution with run-to-target APIs and deterministic headless PNG/WAV capture that is identical across modes.

**Architecture:** A new `chronofork-runtime` crate (core + backend-api only) owns the execution loop, injected host clock, pacer, capture writers and manifest. The CLI composes it with the Mega Drive backend. ADR-0014 records the boundary.

**Tech Stack:** Rust 2024, `chronofork-core`, `chronofork-backend-api`, new `chronofork-runtime`, `chronofork-cli`.

**Spec:** `docs/superpowers/specs/2026-11-17-8.7-execution-modes-capture-design.md`

## Global Constraints

- Canonical state is untouched by pacing: no host clock, sleep or thread scheduling value may enter
  backend state, hashes or artifacts.
- No new third-party dependency; PNG and WAV are hand-rolled with bounded, validated output.
- Capture artifacts contain no host path, hostname, token or wall-clock time.
- The runtime depends only on `chronofork-core` and `chronofork-backend-api`; it never depends on a
  concrete backend, sessions, service, transport or GUI.
- Every task ends with its own tests passing and a commit.

## Review Focus

- A paced run with a fake clock must produce exactly the same bytes as unpaced; a single extra or
  missing step fails the equality test.
- The loop must stop at the requested frame/cycle target and never overshoot a frame boundary.
- PNG: every chunk CRC and the Adler-32 must be correct, lengths must match the IHDR, and a zero
  input must still produce a valid 1×1-compatible encoder path.
- WAV: data length must equal samples × channels × 2 and the header must be little-endian correct.
- Capture must work with no display and no audio device; any host dependency is a typed error.
