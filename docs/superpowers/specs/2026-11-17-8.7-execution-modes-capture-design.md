# Phase 8.7 Design — Execution modes, pacing and headless capture

**Date:** 2026-11-17
**Phase:** `8.7`
**Surface:** `Mixed`
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-17
**Builds on:** Phase 8.2 — master-cycle `Tick` and `Backend::step`; Phase 8.3 — `backend_api::media::{MediaSource, VideoFrame}`; Phase 8.4 — `AudioChunk`; Phase 8.5 — controller input path.

## Goal

Add the normative execution model — `Unpaced`, `Paced` and `Manual` modes with run-to-target APIs
— plus deterministic headless PNG frame and WAV audio capture that is byte-identical in every
mode, without letting host time or host filesystem state reach canonical machine state.

## Approach

**ADR and boundary.** A new accepted **ADR-0014** records the execution model and the boundary:
canonical time is master cycles; pacing is host policy; capture is a pure function of state,
input and the media stream. A new crate `chronofork-runtime` implements the host policy. It
depends only on `chronofork-core` and `chronofork-backend-api` (media seam), never on a concrete
backend, sessions, service, transport or GUI; the CLI composes it with the Mega Drive backend.
This avoids growing `chronofork-sessions` (which owns lifecycle, not host pacing) and keeps the
backend deterministic and unaware of wall time. *Alternatives rejected:* putting the loop in the
CLI (not reusable/testable) and in `chronofork-gui` (presentation-only, and the headless path
must not need presentation).

**Modes and targets.** `ExecutionMode { Unpaced, Paced, Manual }` and
`Target { Frames(u64), Ticks(u64) }`. `run_to_target(backend, sink, target, mode, clock)`
steps the backend until the target is reached or a bounded guard trips, collecting media frames
and audio chunks from `MediaSource`. Unpaced runs as fast as the host allows. Paced waits on an
injected `HostClock` (a trait implemented by the real system clock in production and by a
deterministic `ManualClock` in tests) to hit the video standard's 59.92/49.70 Hz; waiting happens
**between** steps and never changes the step sequence. Manual advances the exact number of
steps/cycles the caller requests and never sleeps. The loop never reads the host clock for
canonical purposes and never passes a wall-clock value into the backend.

**Capture.** `CaptureSink` receives frames and audio; `PngWriter` and `WavWriter` implement it.
PNG is RGBA-8, filter 0 per row, stored (uncompressed) DEFLATE blocks with zlib header and
Adler-32, CRC32 per chunk — no third-party dependency. WAV is RIFF PCM16, stereo, 48 kHz. A
capture manifest records frame count, audio frame count, final tick/state hash, and the SHA-256
of each artifact; it never records a host path, hostname or wall-clock time. The runtime writes
only under an explicit output directory.

**Cross-mode equality.** For the same ROM and input sequence, `Unpaced`, `Paced` (with
`ManualClock`) and `Manual` must produce identical frame bytes, audio bytes, final tick and state
hash. The test runs all three on the same deterministic cartridge and compares artifacts and
canonical outputs; wall time is printed only by the bench surface of 8.6 and is not part of any
capture artifact.

**CLI.** `chronofork megadrive run --rom <FILE> --mode unpaced|paced|manual --frames <N>
[--ticks <N>] [--png-dir <DIR>] [--wav <FILE>] [--manifest <FILE>] [--clock manual]`. Paced uses
the host clock by default; `--clock manual` selects the deterministic clock for reproducible
captures. `--frames` and `--ticks` are mutually exclusive; the command reports the final tick,
state hash and artifact hashes.

**Honesty.** Pacing is presentation policy: the docs state that paced and unpaced runs compute
the same machine and only differ in *when* the host asks for work. No audio-device or display is
required; capture always works headless.

## Tests

- Unit: mode/target validation, pacer math with a fake clock, PNG chunk/CRC/Adler correctness
  against a golden byte fixture, WAV header/length, manifest serialization.
- Integration: `run_to_target` stops at exactly N frames/ticks; a paced run with `ManualClock`
  produces the same artifacts as unpaced; a manual run of the same cycle count matches; capture
  files decode back to the expected dimensions/length; artifacts contain no host path or time.
- CLI: `megadrive run` cross-mode equality on a synthetic cartridge, mutually-exclusive flags
  rejected, missing output directory is a typed error.
- Regression: full gate; synthetic `demo` byte-identical.

## Open Questions

None. The new `chronofork-runtime` crate, 48 kHz PCM16 capture, hand-rolled PNG/WAV and the
`ManualClock`-based parity test were decided with the owner on 2026-11-17.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Pacing leaks host time into canonical state | Non-determinism | Clock injected only into the pacer; backend never sees it; equality tests |
| Hand-rolled PNG encoder is subtly invalid | Unreadable captures | Golden-file decode test with a minimal independent parser; chunk CRCs verified |
| Loop overshoots the target | Wrong frame counts | Target checked after each step; ticks compared against the backend's monotonic tick |
| New crate blurs architecture | Boundary erosion | ADR fixes the dependency direction; a compile-time boundary test/document check |
