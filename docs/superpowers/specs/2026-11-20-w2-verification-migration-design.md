## 1. Census: the real size of the migration

The ADR-0015 §4 figure "**121 `.inspect()` calls and 93 `state_hash` reads**" is a historical
estimate. The reproducible census reproduces the **121** exactly and cannot reproduce the
**93** at any granularity. The migrated surface is materially larger than the ADR implies.
This is a finding, not a quibble: underestimating it is how a "small contract change" turns
into a broken golden suite.

### 1.1 Counting rules (so the numbers are falsifiable)

The census reports **lexical candidate sites** and states the classifier's confidence. It is
not a semantic migration list, and it is not used as a pass/fail gate.

`.inspect()` = a call with an **empty** argument list (both `Backend::inspect()` and
`Session::inspect()`). A second family materializes the same full view and is **not** covered
by the phrase "`.inspect()`" but is covered by the same cost and the same migration:
`SessionManager::inspect(<session>)`. Both are reported.

`state_hash` sites are split by **kind** and, for field accesses, by **receiver confidence**:

| Class | Meaning | Migration effect |
|---|---|---|
| `inspect_read` | `<expr>.inspect()` | view split (§5) |
| `inspect_read_keyed` | `<x>.inspect(<session id>)` | view split (§5) |
| `hash_field_read` + receiver `outcome` | a step outcome's field | **W2 edits this** |
| `hash_field_read` + receiver `other` | `inspection`/`machine`/`snapshot`/`self` ... | not `StepOutcome`; re-cost, do not edit for §2 |
| `hash_field_read` + receiver `unknown` | receiver not decidable lexically | needs typing before it is scheduled |
| `hash_struct_init` | `state_hash: expr` in a struct literal | a **write**, not a read — no migration |
| `hash_method_call` | `.state_hash()` accessor | keeps compiling; re-cost |
| `hash_value_other` | bare `state_hash` value | edit |
| `hash_decl` | `fn state_hash` | the single serializer (§3) — must stay exactly 1 in production |

The production/test split uses the `/tests/` path convention; `#[cfg(test)] mod tests` **inside
a production file** is not separable lexically and is reported as production, with the
`megadrive/src/backend.rs` row called out explicitly in §1.3.

2. the **93 does not reproduce at any granularity** tested. The candidate readings are 273

   reads. The figure is a floor, not a count;
3. `SessionManager::inspect(<session>)` materializes the same full view and is **not** counted

number of *empty-argument `.inspect()` calls*", which is a well-defined quantity on both sides.
Recommend an appended measured addendum to ADR-0015 §4 rather than editing the clause: the
decision does not change, only the estimate of its blast radius.

### 1.4 The four full-state paths (why `step` alone is not enough)

ADR-0015 §4 names four paths that derive from the full state body. Today:

|---|---|---|---|
| `step` | `crates/chronofork-megadrive/src/backend.rs:632-685` | yes, every step | no |

### 1.5 The worktree moves: pin every measurement

The worktree `agent/consolidation-adrs-2026-11-20` is **shared and actively edited**. While
this spec was being written, W3.1 (per-session lock + registry) was landing in the same tree
and changed the call-site counts underneath the census:

| Snapshot | Manifest digest | Files | `.inspect()` | `.inspect(id)` | `.state_hash` field | `hash_decl` |
|---|---|---:|---:|---:|---:|---:|
| committed `b8d63a1` (the numbers in §1.2/§1.3) | `26246f89…` | 214 | 121 | 112 | 273 | 12 |
| live worktree, mid-W3.1 | `e2a17885…` | 218 | 133 | 106 | 277 | 12 |

The delta is **W3.1's**, not noise: `manager.rs` changed the session access path from
`self.session(id)?.inspect()` to `self.session(id)?.lock()?.inspect()`, which moved
`.inspect(id)` receivers into the `.inspect()` class, and W3.1 added
`w3_scale_probe.rs`, `w3_lifecycle_probe.rs` and `w3_concurrency.rs` test files plus the
`chronofork-transport` wiring. No W2-decided behavior changed; 233 → 239 inspection
materializations are the same requirement counted twice.

`hash_decl` is **12 in both snapshots**, which is the point of the fixed classifier (§1.6):
the number of `fn state_hash` definitions is a property of the contract, not of whoever is
editing the tree. The value-read totals differ between the two rows (513 vs 517) only because
W3.1 added test files; the baseline row is the one quoted in §1.2.

**Consequences, and what this spec does about it:**

1. Every count in §1.2/§1.3 is bound to the **committed baseline digest**, so it is
   reproducible from a clean checkout and cannot silently drift.
2. The census reports a `tree_manifest_digest` and accepts `--expect-manifest <digest>`
   (exit 3 on drift), so a future run states which tree it measured instead of quietly
   reporting a different number.
3. The generated `census.md`/`census.json` in
   `.research/implementation-2026-11-20/` are the **live** snapshot and carry their own digest.
   A reviewer comparing the two must compare digests first.
4. W2 should re-run the census at each landing (§11.5) and diff against the digest recorded in
   that landing's commit, not against §1.2 — the baseline is a frozen reference, not a target
   that the live tree must still match.

This is also the practical argument for the declaration in §8: a public API break whose blast
radius is counted from a moving tree has no verifiable "done" condition. The manifest is that
condition.

### 1.6 The classifier bug R2 found, and its fix (R2-5)

R2 reproduced a real defect: `fn state_hash(&self) -> Result<...>` was classified as a
**call**, because the call pattern was tried before the declaration pattern and claimed the
same span. Two consequences, both visible in the first revision of this spec:

- the census reported `hash_decl = 0` while the spec text asserted there was exactly **one**
  canonical `state_hash` implementation — an internal contradiction;
- `fn inspect(...)` was unaffected, but the same ordering was a latent hazard.

The fix, and what it changed:

| Change | Before | After |
|---|---|---|
| declaration checked **before** call | `hash_decl = 0` | `hash_decl = **12**` |
| `state_hash: expr` in a struct literal | counted as a **read** | `hash_struct_init` — a **write** |
| receiver classification | none | `outcome` / `other` / `unknown` |
| production vs `/tests/` split | one merged table | two tables + counts |
| schema | `chronofork.w2.census.v1` | `chronofork.w2.census.v2` |

Reproducing the fix (from a clean checkout of the baseline):

```sh
git archive b8d63a1 | tar -x -C /tmp/b8d63a1
cd /tmp/b8d63a1 && python3 <worktree>/.research/implementation-2026-11-20/tools/w2_census.py \
    --repo-root . --out /tmp/baseline-census --expect-manifest 26246f89...
```

Two invariants the tool now self-checks in the spec's own review, not in code:
`inspect_read + inspect_read_keyed` must equal the number of `.inspect(` call sites, and
`fn state_hash` is the only `hash_decl` in production.

## 2. D1 — `StepOutcome` without a mandatory hash

### 2.1 Target shape

```rust
/// Result of one execution step.
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub struct StepOutcome {
    /// Tick after the step.
    pub tick: Tick,
    /// Whether the machine halted during this step.
    pub halted: bool,
    /// Whether this outcome was produced by a verified path.
    ///
    /// `false` for `Backend::step` after `W2-3`; `true` for
    /// `Backend::step_verified`. A harness that needs a per-step digest must
    /// either call `step_verified` or call `Backend::state_hash()` itself.
    pub verified: bool,
}
```

### 2.2 The migration window (why `verified` exists)

The field is removed in three ordered, individually testable landings. The order matters: with
`step` still hashing, existing code keeps compiling and the new API is proved before any
behavior changes.

| Landing | `StepOutcome` | `step` behavior | Gate |
|---|---|---|---|
| **W2-1** | `{ tick, halted, state_hash: Option<StateHash>, verified: bool }` | unchanged (still hashes, `Some`) | `cargo test --workspace` green with **zero** behavior change; `hash_single_source` lands |
| **W2-2** | same | `state_hash = None`, `verified = false` | twin-machine invariant green; goldens re-recorded or read through `step_verified` |
| **W2-3** | `{ tick, halted, verified }` | unchanged from W2-2 | all 279 production + 227 test sites migrated; census shows no stale field read |

Why not go straight to the target: between W2-1 and W2-3 the callers must be told *loudly*
when they read a digest that is no longer there. `Option` makes the compiler enumerate every
site, and `verified` makes it impossible to silently treat an unverified outcome as a verified
one (migration safety, not performance). `verified` is kept in the target shape because a
replay harness legitimately wants to know whether the outcome it received carries a per-step
guarantee, and because removing it later is a cheap, separate break.

### 2.3 Accessor (optional, migration convenience)

```rust
impl StepOutcome {
    /// Returns the hash when this outcome carries one.
    ///
    /// Migration helper. In the target shape (`W2-3`) this method is removed and
    /// callers use `Backend::state_hash()` or `step_verified`.
    #[must_use]
    pub const fn state_hash(&self) -> Option<StateHash> { self.state_hash }
}
```

`StateHash` is `Copy` (`crates/chronofork-core/src/hash.rs:14-27`), so returning it by value
adds no allocation. A `debug_assert!(self.verified)` in the accessor is **not** used: the
accessor exists precisely for the ordinary path during the window.

### 2.4 Explicitly rejected alternatives

| Alternative | Why not |
|---|---|
| Keep `state_hash` as a mandatory field and micro-optimize | ADR-0015: the measured ceiling is ~0.5–1 fps; reordering pieces does not remove the 197 KB + SHA path. |
| `Option<StateHash>` as the **final** shape | An always-`None` field on the hot path is a standing invitation to re-add the cost, and it forces every consumer to handle a state the design forbids. Use it for the window only. |
| `state_hash: StateHash` zeroed when unverified | Silent lie: a zero digest is a valid-looking value. The 2026-11-20 review instrumentation had to zero the hash to ablate the cost; that is a measurement build, not a contract. |
| Put the hash behind a feature flag | Two builds, one contract; determinism claims become build-dependent. ADR-0015 already rejects this shape (`VerificationPolicy` is a runtime policy, not a feature). |

## 3. D2 — one canonical hash source, on demand

### 3.1 Trait additions

```rust
pub trait Backend: Send {
    // existing: descriptor, step, snapshot, restore, inspect, read_memory,
    //           write_memory, debug_access, media_mut

    /// Computes the canonical state digest without changing any state.
    ///
    /// There is exactly one canonical computation in the implementation. The
    /// verified path *calls* this; it must never re-implement the serializer.
    ///
    /// # Errors
    /// Returns a typed error when the implementation cannot produce the digest.
    fn state_hash(&self) -> Result<StateHash, BackendError>;

    /// Advances the machine by one quantum and produces a per-step digest.
    ///
    /// The default implementation is the composition of `step` and
    /// `state_hash`, so it can never drift from the single canonical source:
    ///
    /// ```ignore
    /// fn step_verified(&mut self, input: InputFrame) -> Result<VerifiedStepOutcome, BackendError> {
    ///     let outcome = self.step(input)?;
    ///     let hash = self.state_hash()?;
    ///     let state_hash = self.state_hash()?;
    ///     Ok(VerifiedStepOutcome {
    ///         tick: outcome.tick,
    ///         halted: outcome.halted,
    ///         state_hash,
    ///         verified: true,
    ///     })
    /// }
    /// ```
    ///
    /// A backend whose batch primitive must interleave hashing (to amortize
    /// serialization) overrides this **only** to call `state_hash()` on the same
    /// state the ordinary path just produced.
    fn step_verified(&mut self, input: InputFrame) -> Result<VerifiedStepOutcome, BackendError> {
        let outcome = self.step(input)?;
        let state_hash = self.state_hash()?;
        Ok(VerifiedStepOutcome {
            tick: outcome.tick,
            halted: outcome.halted,
            state_hash,
            verified: true,
        })
    }
}
```

`state_hash()` has **no default body**. A default would have to either fabricate a value
(forbidden) or require an `Unsupported` variant that every backend would then be tempted to
return; requiring the method makes each backend state its canonical digest explicitly. There
is exactly **one** implementor that is not a test double
(`crates/chronofork-megadrive/src/backend.rs`), so the cost of no default is one method per
implementor. The test backend already computes an equivalent digest
(`crates/chronofork-test-backend/src/lib.rs:19`), so it satisfies the method directly.

`VerifiedStepOutcome` is a **distinct type**, not `StepOutcome` with a field. That is what
makes the twin-machine test meaningful: the two paths return different types, and the test is
the only place that compares them.

```rust
/// Result of one verified execution step.
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub struct VerifiedStepOutcome {
    /// Tick after the step.
    pub tick: Tick,
    /// Whether the machine halted during this step.
    pub halted: bool,
    /// Digest of the state after the step.
    pub state_hash: StateHash,
    /// Always `true`. `step_verified` is the only producer, and the field is a
    /// compile-time declaration of that fact for callers that receive an outcome
    /// through a generic path.
    pub verified: bool,
}
```

`StepOutcome.verified` is `false` for `Backend::step` and `true` for the value
`step_verified` returns. These are the **only** two definitions of the flag; §10's hand-off
list must not claim otherwise (this correction is R2-1).

`BackendError` gains one variant, used by the bounded-input and bounded-batch paths and by
nothing else:

```rust
/// A bounded request exceeded a declared backend limit.
Limit {
    /// The limited field, named for diagnostics.
    field: &'static str,
    /// The declared limit.
    limit: u64,
    /// The value that was requested.
    requested: u64,
},
```

A `String`-carrying or `Internal` error would hide a caller-fixable condition behind an
opaque message (AGENTS.md: explicit typed errors, no stringly errors). `BackendError` is not
an exhaustive public enum for downstream matches in a way that would make this additive, so it
is declared with the rest of the break in §8.

### 3.2 The single-source invariant, stated precisely

The failure mode the ADR guards against (R1-C1): `step_verified` becomes a second serializer
that happens to agree today and drifts tomorrow. The rule is therefore structural, not
behavioral:

1. **One serializer.** `state_body`/`state_body_bytes` in
   `crates/chronofork-megadrive/src/backend.rs:454-513,1169-1263` remains the only writer of
   the serialized field layout. `state_hash()` and the snapshot both derive from it today and
   must continue to.
2. **No duplicated chain.** `MegadriveBackend::state_hash()` is a private inherent method with
   a deliberate codegen-motivated duplication of the *view construction*
   (`crates/chronofork-megadrive/src/backend.rs:481-513`) whose own doc comment records that
   routing it through `state_body_bytes` measured ~18% slower in `bench_step`. W2 **keeps** that
   optimization and the doc comment, and exposes it through the trait method. It must not be
   "cleaned up" into a second serializer — it already is not one (both call `state_hash_for`).
3. **Verified path calls it.** The default `step_verified` literally calls `self.state_hash()`.
   A backend override may only reorder, never recompute.
4. **Test.** §11.1 `hash_single_source` pins (1)–(3) at the type and value level.

### 3.3 Errors

`BackendError` gains exactly one variant for the bounded paths (see §3.1). A backend that
cannot produce a digest is a defect in that backend, not a caller error, so `state_hash()`
returns the existing typed errors from its serialization path; the test backend's digest path
is infallible and returns `Ok`.

## 4. D3–D5 — batch execution, stop grammar, cancellation

### 4.1 Ownership (ADR-0015 §3, R1-C3/C10)

| API | Owner | Contract |
|---|---|---|
| `step` | `Backend` | one instruction, no hash |
| `step_verified` | `Backend` | one instruction, with digest |
| `run_until` / `run_cycles` | `Session` (`chronofork-sessions`) | composition over the backend primitive |
| **exactly one** batch primitive | `Backend` | the efficient machine loop |
| `run_frame` | **capability** | offered only where a frame boundary is identifiable |

The single batch primitive:

```rust
/// What ends a bounded run, independent of the stop conditions.
///
/// The budget is a first-class parameter of the **one** batch primitive: there is
/// no separate `steps: u64` argument, because an instruction budget and a cycle
/// budget are two readings of the same question and a second parameter would let
/// a caller pass both.
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub enum StopBudget {
    /// Stop when the machine halts, a condition matches, or the run is cancelled
    /// or reaches its deadline. There is no step or cycle ceiling: the caller
    /// supplies one of the other variants when it wants one.
    Unbounded,
    /// Stop after at most this many instructions.
    Steps(u64),
    /// Stop at the first step boundary at which **consumed master cycles** are at
    /// or above this. Never converted into an instruction count up front: a step's
    /// cost is the backend's business and may vary per instruction.
    Cycles(u64),
}

impl StopBudget {
    /// Returns true once `performed` steps and `cycles` consumed satisfy the budget.
    #[must_use]
    pub const fn is_exhausted(&self, performed: u64, cycles: u64) -> bool;
}

/// Advances at most `budget` under `control`, stopping early on a matched
/// condition. Deterministic: the same inputs, budget and observed signals produce
/// the same `performed`.
fn run_batch(
    &mut self,
    inputs: &InputSequence,
    budget: StopBudget,
    stop: &StopSet,
    policy: &VerificationPolicy,
    control: &RunControl,
) -> Result<BatchOutcome, BackendError>;
```

The loop checks `budget` at every boundary, in the same place it checks the signals and
conditions, so a cycle budget never becomes a pre-computed step count:

```rust
// inside the one loop, after the signals and a `pre-step` condition:
if budget.is_exhausted(performed, cycles) {
    return Ok(BatchOutcome { .., stop_reason: StopReason::Completed });
}
// ... take one step, accumulate `cycles += step_cycles`, then re-check the signals ...
```

`Session` maps its two entry points onto that one parameter and nothing else:

| Session entry point | `budget` it passes | Stop conditions |
|---|---|---|
| `run_until(stop, steps, ...)` | `StopBudget::Steps(steps)` | the caller's `StopSet` |
| `run_cycles(cycles, ...)` | `StopBudget::Cycles(cycles)` | the caller's `StopSet` |
| a service "run until X" with no ceiling | `StopBudget::Unbounded` | the caller's `StopSet` |

The independent step ceiling is preserved because it is the same mechanism: a caller that
wants both passes `Steps(n)` and adds a tick condition, and `run_batch` honours whichever
fires first under the precedence table in §4.2.

**There is exactly one batch primitive on `Backend` (R2b-B).** An earlier revision also added
`Backend::run_cycles`, which is a second batch loop by another name and contradicts ADR-0015
§3/R1-C3 ("at most one batch primitive where the backend can be efficient"). The cycle budget
is a **session** concern: `Session::run_cycles` expresses it as the `budget` argument of the one
primitive **above** -- not as a declared enum with no caller-facing connection, which was the
R2c gap. There is one loop, one precedence table and one place to cancel.

`BatchOutcome::performed` remains instructions and `BatchOutcome::cycles` remains consumed
master cycles, so the units stay explicit even though there is one loop.

`BatchOutcome { performed, cycles, tick, halted, stop_reason, stop_condition: Option<MatchedStop> }`.
`performed` counts **instructions**; `cycles` counts **consumed master cycles**. They are not
the same unit and the result carries both, so a caller never has to guess (§4.5).
The backend owns the loop because only it can stop without a session round trip; the semantics
(signals, precedence, what `stop_on` means) live in `chronofork-backend-api` so every backend
shares one grammar. A backend that cannot implement the primitive uses the crate-provided
default (`for _ in 0..budget { self.step(...) }` plus the signal checks) and stays correct,
only slower — the same shape as `debug_access`/`media_mut` today.

**Anti-slop note.** The default `run_batch` and the trait method must not both become "the
implementation". The default is the reference semantics; the megadrive override exists only to
avoid the round trip. The twin-machine test runs against **both**.

### 4.2 Stop grammar and precedence (contract, not implementation detail)

Frozen from ADR-0016 §"New limits and crate boundary":

```rust
pub enum StopKind { Pc, Memory, Event, Tick, Frame }
pub enum StopPhase { PreStep, PostStep }   // default PostStep
pub enum StopValue {
    Pc(u32),
    Memory { address: u32, mask: u16, expected: u16 },
    Event(DebugEventKind),
    Tick(Tick),
    Frame(u64),
}
pub struct StopCondition { pub kind: StopKind, pub value: StopValue, pub phase: StopPhase }
pub struct StopSet { /* at most 4 conditions, in request order */ }
pub enum StopReason { Cancelled, Deadline, Halted, StopCondition, Completed }
/// The single matched condition, when `stop_reason` is `StopCondition`.
pub struct MatchedStop { pub kind: StopKind, pub value: StopValue, pub request_index: u8 }

impl StopSet {
    /// Rejects more than four conditions (ADR-0016 F8) instead of silently
    /// dropping the tail.
    pub fn new(conditions: Vec<StopCondition>) -> Result<Self, BackendError>;
}
```

The reason `Deadline` sits inside `StopReason` (a value that reads like a canonical outcome)
is deliberate: the caller must be told why the run ended, and the ADR fixes one
`stop_reason` reading. The deadline itself never enters canonical state — it is an
`Instant` on `RunControl`, and only `performed`/`tick` do.

- `pre-step` tests **before** the next step and stops **without** consuming it.
- Tie-break among conditions matching at the same boundary:
  `pc > memory > event > frame > tick`; same kind → lowest address/index; same kind **and**
  address → **request position**.
- Same-boundary priority (total order): `cancelled > deadline > halted > stop_condition >
  completed`. Simultaneous cancel + deadline ⇒ `cancelled`.
- The result carries exactly one `stop_reason`; when it is `stop_condition` the matched
  condition is named (`kind`, `value`, `request_index`).

Implementation consequence: the signal checks and the condition tests must be in **one**
function with **one** precedence table, not scattered across `if`s. The table is data; the
tests below pin every adjacent pair (cancel/deadline, deadline/halt, halt/condition,
condition/completed) and the tie-break inside the condition set.

### 4.3 Cancellation is lock-free (ADR-0015 §3.1, R5-K2/K3)

```rust
/// Cooperative cancellation and host deadline for one run.
///
/// The cancel flag is shared through an atomic so any thread can set it. The
/// deadline is **immutable after construction**: `Clone` copies it, so a clone can
/// never disagree with the original about when the run must stop. Configuring the
/// deadline is a builder step performed *before* the control is shared, which is
/// what makes a `&self` setter unnecessary (and a `Cell`/`Mutex` unnecessary).
#[derive(Clone, Debug, Default)]
pub struct RunControl {
    cancel: Arc<AtomicBool>,
    deadline: Option<Instant>,
}

impl RunControl {
    /// Not cancelled, no deadline.
    #[must_use]
    pub fn new() -> Self;
    /// Sets the host deadline **before** the control is shared.
    #[must_use]
    pub fn with_deadline(self, at: Instant) -> Self;
    /// Requests cancellation. Lock-free; valid from any thread holding a clone.
    pub fn cancel(&self);
    #[must_use]
    pub fn is_cancelled(&self) -> bool;
    #[must_use]
    pub const fn deadline(&self) -> Option<Instant>;
}
```

**Why not `set_deadline(&self)` (R2-1).** An earlier revision of this spec wrote that, which
cannot compile against `Option<Instant>` without a lock or cell. The builder form is the
honest fix: the deadline is host policy fixed at the start of the run, and making it immutable
after sharing removes a whole class of "the clone has a different deadline" bugs at zero cost.

`RunControl` is deliberately not `Copy`; `Clone` shares the cancel flag and copies the
deadline.

- The stepping loop reads the atomic at **every instruction boundary**, including inside
  `run_batch`. It never acquires the session registry, the service manager lock or a transport
  worker — those are the resources the run itself occupies.
- Granularity is deterministic and **reported**: the acknowledgment promises nothing; the
  authority is `performed`/`tick`/`stop_reason`.
- `Instant` is **host policy**, never canonical state (ADR-0014/0015; AGENTS.md rule 10). It
  chooses `k`; it is never replayed. A run record stores `k` and the inputs.
- A cancelled or deadline-truncated run is a valid deterministic **prefix**; it reports
  `performed = k` and a stop reason even when the envelope is a typed error (R5-K3).

Rejected: one global cancel flag (cross-talk between sessions), a `Mutex<bool>` (queues behind
the run it must stop), a per-session `AtomicBool` only (two concurrent runs in one session
would share a flag — v1 forbids that via the writer lease, but the token is per run so the
invariant does not depend on the lease).

### 4.4 `Session` composition

```rust
impl Session {
    /// Bounded run over instructions, with the caller's verification policy.
    ///
    /// `steps` is the caller's instruction ceiling and becomes
    /// `StopBudget::Steps(steps)` on the one backend primitive; it is not a second
    /// budget mechanism.
    pub fn run_until(
        &mut self,
        stop: &StopSet,
        steps: u64,
        inputs: &InputSequence,
        policy: &VerificationPolicy,
        control: &RunControl,
    ) -> Result<RunOutcome, SessionError>;

    /// Bounded run over master cycles.
    ///
    /// A thin composition over `run_until`: it passes `StopBudget::Cycles(cycles)`
    /// to the single backend primitive, which checks it at every step boundary
    /// against the cycles actually consumed. It is **not** a second batch loop, and
    /// it never converts cycles into a fixed instruction count.
    pub fn run_cycles(
        &mut self,
        cycles: u64,
        stop: &StopSet,
        policy: &VerificationPolicy,
        control: &RunControl,
    ) -> Result<RunOutcome, SessionError>;

    /// Cheap status projection.
    pub fn status(&self) -> Result<MachineStatus, SessionError>;
}

pub struct RunOutcome {
    pub performed: u64,
    pub cycles: u64,
    pub tick: Tick,
    pub halted: bool,
    pub stop_reason: StopReason,
    pub stop_condition: Option<MatchedStop>,
    /// Present only when the policy actually produced one; `None` for `None`/`OnDemand`.
    pub state_hash: Option<StateHash>,
}
```

`Session::run_until` does not re-implement the loop: it delegates to `Backend::run_batch` and
adds the session checks. Session state checks (`ensure_open`, `SessionState::Ready`) behave
exactly as in `Session::step` (`crates/chronofork-sessions/src/session.rs:135-148`).
`state_hash` on `RunOutcome` is `Some` only when the policy produced a digest, so a caller
never receives a placeholder it might mistake for a verified value.

### 4.5 Units, policy, and inputs (R2-2)

Three things an earlier revision left implicit and which decide whether the contract is
executable.

**Units.**

| Quantity | Unit | Where it appears |
|---|---|---|
| `performed` | **instructions** (backend quanta) | every `BatchOutcome` |
| `cycles` | **consumed master-clock cycles** | every `BatchOutcome` |
| `tick` | absolute master-clock cycles | every outcome |
| `steps` (batch budget) | instructions | `run_batch` |
| `cycles` (cycle budget) | master cycles | `StopBudget::Cycles` on the one batch primitive |
| `max_wall_ms` | host milliseconds | `RunControl` deadline only |

The cycle budget's semantics, fixed and now **executable at the backend level** because
`StopBudget::Cycles` is a parameter of the one primitive (R2c): the harness probes
`cycles_budget_stops_at_the_first_boundary` (a 1.5-step budget lands on the **second** step --
a pre-computed `budget / step_cycles` would have stopped on the first) and
`cycles_and_steps_are_independent_levers` (a cycle budget, a step ceiling and `Unbounded` with
a condition each end the run for their own reason). A `Cycles` budget is never converted into
an instruction count. A caller that wants an independent step ceiling passes
`StopBudget::Steps` and adds a `tick` condition; the two then compete under the §4.2 precedence
table.

1. a step consumes `cycles_of_step` master cycles, decided by the backend;
2. the run stops at the **first step boundary at which consumed cycles >= the budget**;
3. therefore `outcome.cycles >= budget` and `outcome.cycles - budget < cycles_of_step` —
   the overshoot is at most one step and is reported, never hidden;
4. `run_cycles(0)` executes nothing and reports `performed = 0`, `cycles = 0`,
   `stop_reason = Completed`;
5. a halted machine reports `Halted` with `performed = 0`;
6. Ticks and cycles are **not** interchangeable: `tick` is absolute, `cycles` is the
   consumption of this run. A test asserts both (scaffold `cycles_are_master_cycles_*`).

**Policy during a batch.** The policy decides hashing *per step*, inside the same loop, so
there is one stepping logic and one precedence table:

| Policy | Behavior inside `run_batch` |
|---|---|
| `None` (ordinary default) | `step`; zero digests |
| `EveryStep` | `step_verified`; exactly one digest per step |
| `EveryN(n)` | `step_verified` at 1-based multiples of `n` (steps 1, n+1, 2n+1 ...), `step` otherwise |
| `AtTick(t)` | `step_verified` at the step whose resulting tick is `t`, `step` otherwise |
| `OnDemand` | `step`; the digest is the caller's explicit `state_hash()` after the run |

`EveryN(n)` means "one digest every `n` steps, starting at the first": steps 1, n+1, 2n+1,
... Over 15 steps with `n = 5` that is exactly 3 digests (the scaffold asserts 3, not "about 3"). The policy is a parameter of the batch
primitive, not a session-level mode, so two concurrent runs in one process cannot influence
each other's verification.

**Inputs.** `InputSequence` is a bounded sequence of the existing canonical `InputFrame`
encoding — no new wire type:

| Rule | Behavior |
|---|---|
| bound | `max_input_frames = 4096`; a longer sequence is a typed `Limit` error at construction |
| shorter than the budget | padded with `InputFrame::NEUTRAL` |
| **longer than the budget** | typed `Limit { field: "input_frames" }`, **rejected before any step executes** |
| neutral, non-neutral | the sequence is real input; a non-neutral frame must change canonical state versus a neutral run |

The "rejected before any step" rule is the one that matters for correctness: a run that
executes 100 steps and *then* discovers the input sequence was invalid has already mutated
canonical state and cannot be retried safely. The scaffold asserts the pre-mutation digest is
unchanged on rejection.

## 5. D6 — cheap `status()`, no hashing in `inspect()`

### 5.1 Split in `chronofork-backend-api`

```rust
/// Upper bound the register maps must respect in every backend.
pub const MAX_STATUS_REGISTERS: usize = 64;

/// Cheap status: no digest, no RAM copy.
#[derive(Clone, Debug, Eq, PartialEq)]
pub struct MachineStatus {
    pub tick: Tick,
    pub halted: bool,
    /// The 68000/core register file (`d0..d7`, `a0..a7`, `pc`, `sr`, ...).
    pub cpu_registers: BTreeMap<String, u64>,
    /// Device pseudo-registers (`vdp_status`, `mapper.bank*`, `sram.*`, `tmss.*`,
    /// `scheduler_*`), kept **separate** from the CPU file.
    pub device_registers: BTreeMap<String, u64>,
    /// Frame index at this tick (the render boundary identity).
    pub frame_index: u64,
}

impl MachineStatus {
    /// Merged view for a consumer that wants one map (the GUI/CLI printers).
    #[must_use]
    pub fn registers(&self) -> BTreeMap<String, u64>;
}

/// On-demand inspection view. Still split, still no digest.
#[derive(Clone, Debug, Eq, PartialEq)]
pub struct MachineInspection {
    pub tick: Tick,
    pub halted: bool,
    pub frame_index: u64,
    pub cpu_registers: BTreeMap<String, u64>,
    pub device_registers: BTreeMap<String, u64>,
    /// The memory window, only when the caller asked for it.
    pub memory: Option<MemoryWindow>,
}

pub struct MemoryWindow {
    pub base: u64,
    pub bytes: Vec<u8>,
}
```

**Why the split is not just two flat maps (R2-5).** ADR-0015 §4/R1-C5 requires device
pseudo-registers (VDP/cartridge/TMSS) to be **separated** from the 68000 registers. A single
flat `BTreeMap<String, u64>` with dotted key names would make the separation a naming
convention a consumer can violate; two fields make it structural, and `registers()` keeps the
one-map consumers (GUI/CLI printers, service JSON) simple. `MAX_STATUS_REGISTERS` bounds
`cpu_registers.len() + device_registers.len()` together.

`MachineInspection` keeps its role as the **on-demand** view:

| Field | Today | After W2 |
|---|---|---|
| `tick` | present | present |
| `state_hash` | present, **computed** | **removed** from the struct; a caller that wants it calls `Backend::state_hash()` |
| `halted` | present | present |
| `registers` | present | present (same map) |
| `memory_base` / `memory` | present, always a 64 KiB copy | **moved** to an opt-in `memory: Option<MemoryWindow>` (or a separate `read_memory` call) |

`inspect()` returning the register map is why `status()` cannot be "tick, PC, halted" only
(ADR-0015 §4, R1-C5). `status()` is a **projection** of the same builder `inspect()` uses, so
the register map has one writer.

**Bounded-`BTreeMap` honesty.** The current megadrive `inspect()` builds ~44 registers
including hardware-readable pseudo-registers (`crates/chronofork-megadrive/src/backend.rs:883-977`).
`BTreeMap` is not free, but it is what the debugger, the trace layer, the GUI decoders and the
service JSON already consume — a different representation would be a second contract. Keep
`BTreeMap` and make the bound explicit and tested (`MAX_STATUS_REGISTERS`, and an insertion
count assertion per backend), rather than inventing an index-keyed view now. If a benchmark
later shows the map allocation dominates `status()`, that is a separate, measured change.

`MachineStatus`/`MachineInspection` are **additional public breaks** on top of `StepOutcome`
and are declared with it, under the same 0.x semver clause.

### 5.3 Service JSON, the API wire version, and the MCP protocol (R2-4)

`AppService::run` writes `"state_hash"` into the response
(`crates/chronofork-service/src/service.rs:461-491`) and `inspect` writes a full `machine`
object. The GUI decodes both strictly. Two different version numbers must not be conflated,
and an earlier revision of this spec did conflate them:

| Version | Value | Who owns it | W2's action |
|---|---|---|---|
| **ChronoFork API wire version** | v1 today → **v2** in this landing | ADR-0016 §Compatibility | W2 **is** the landing that changes the shape, so W2 introduces v2 |
| **MCP protocol version** | `2025-03-26` | the MCP adapter | **unchanged**; the `2026-07-28` migration stays deferred (ADR-0016) |

**The MCP protocol is not bumped by W2.** Only the ChronoFork API version moves, and it moves
through the negotiation ADR-0016 already fixes:

- the client sends its version range on **every** request (`X-ChronoFork-API: 1` / `2`, or the
  MCP `initialize` + per-call equivalent); a request **without** a version field is treated as
  **v1**;
- a **new server** rejects an incompatible version **before dispatch**, with a typed
  `unsupported_version` and **no partial execution**;
- a **new client** against a legacy server performs a **read-only** `capabilities` probe before
  any v2 mutation and fails locally if v2 is not advertised; the probe never mutates;
- a **legacy server** is not required to reject anything: it ignores the field and dispatches
  as v1. The guarantee lives in the client, because a deployed daemon cannot be retrofitted.

**Declared matrix** (from ADR-0016; W2 declares it, W3.6 implements the client half):

| Client | Server | Result |
|---|---|---|
| v1 | v1 | v1 shape (unchanged; `state_hash` present as today) |
| v1 | v2 | server serves the **v1 shape** for the v1 call |
| v2 | v1 / legacy | client refuses v2 **locally** after the read-only probe; v1 calls use the v1 shape |
| v2 | v2 | v2 shape: `run` gains `performed`, `cycles`, `stop_reason`, request/revision keys |

**What W2 can claim, and what it cannot.** W2 changes the server-side shape and declares v2
plus the pre-dispatch refusal. It **cannot** declare the landing wire-compatible on its own,
because the client-side probe and the GUI/typed-client decoders are the other half of the
matrix (ADR-0016 W3.6). The honest statement is therefore:

- the **v1 shape remains served** for unversioned/v1 calls, so existing clients are not broken
  by the landing;
- the **v2 shape** is served only to a caller that asks for v2;
- the read-only probe, the client-side local refusal, and the GUI decoder migration are
  **prerequisites for claiming v2 end-to-end compatibility**, and they are not W2's to write;
- until they land, W2's wire change is **served but not promoted**: no docs claim v2 support
  beyond the declared matrix above.

`state_hash` stays present in the `run`/`inspect` responses (the service computes it
deliberately, once per operation). The contract change is that it is no longer **free per
step**, not that the wire loses the field.

## 6. D7 — render at the boundary

Current behavior: `capture_frame()` clones the VDP, calls `finish_frame()`, converts palette
indices to RGBA and stores a 320×224×4 = **286,720 B** frame in a one-slot queue on every frame
boundary (`crates/chronofork-megadrive/src/backend.rs:717-742`), whether or not a consumer
takes it.

**W2 keeps that boundary and does not depend on changing it.** ADR-0015 §5 and R1-C6 are
explicit: there is no production frame consumer, so "skip render when nobody asks" **deletes
the artifact** instead of economizing it; render is ~7.6% of a 16.67 ms budget and is **not** a
prerequisite for the interactive target. Consequences for this spec:

1. **Not in W2's core contract.** W2.6 stays the optional, separately measured branch in the
   plan; W2.7 does not gate on it.
2. **If pursued**, the rule is: preserve the frame index/window and enough boundary state to
   reconstruct the frame on demand; never render future state at `take`. The local gate is
   "bytes identical with and without a consumer".
3. **The reconstruction substrate W2 does provide** is `MachineStatus::frame_index` (§5.1),
   which gives the boundary identity a lazy implementation needs and which the service needs
   anyway for `frame`-kind stop conditions (§4.2).
4. **Frame format, budget, pagination and the round-trip test are W3.4a**, not W2.

## 7. D8 — persistent buffers, `Arc`, `reap()`

### 7.1 Persistent buffers (R2-5)

`state_body` builds a `Vec<u8>`; the payload is body + magic + version, ~197 KB serialized
(RAM alone is 64 KiB and VRAM 64 KiB). ADR-0015 §6 decides **buffer reuse**, not merely
"fewer allocations". An earlier revision of this spec deferred that reuse on a justification
that does not hold: `&self` does **not** make interior mutability impossible. `Backend` is
`Send` but **not** `Sync`, and a session serializes access to its machine with `&mut self`
during a run, so a per-machine scratch buffer behind `RefCell` is sound here.

**Decision: implement the reuse**, with the single-threaded contract stated in the type.

```rust
// In the machine -- owned, no `Rc`:
/// Reused state-body buffer; capacity is kept across calls.
///
/// `RefCell` gives interior mutability to a `&self` read, and a plain
/// `RefCell<Vec<u8>>` is `Send` when `Vec<u8>` is, so the machine stays `Send` as
/// `Backend` requires. `Rc<RefCell<Vec<u8>>>` would **not**: `Rc` is not `Send`, and
/// wrapping the scratch in it breaks the trait bound (R2b reproduced E0277).
/// Nothing here needs a shared handle -- the buffer belongs to exactly one machine.
scratch: RefCell<Vec<u8>>,

impl MegadriveBackend {
    /// Writes the canonical state body into `out`, clearing it first.
    fn write_state_body_into(&self, out: &mut Vec<u8>) {
        out.clear();
        // one writer for the field layout: `state_body` writes into `out`
        state_body_into(out, &StateView { /* ... */ });
    }
}

// In `impl Backend`:
fn state_hash(&self) -> Result<StateHash, BackendError> {
    // One borrow for the length of the call. `write_state_body_into` takes `&self`
    // and the buffer separately, so no `Ref` is held across a second borrow of the
    // same cell.
    let mut out = self.scratch.borrow_mut();
    self.write_state_body_into(&mut out);
    Ok(hash_state_body(&out))
}

fn snapshot(&self) -> Result<BackendSnapshot, BackendError> {

Rules the implementation must follow, or the reuse becomes a correctness bug:

1. **One writer.** `write_state_body_into` is the only writer of the serialized field layout;
   `state_hash`, `snapshot` and the restore validator all consume it. The existing
   codegen-motivated "hash without an intermediate `Vec`" optimization in `state_hash()`
   (`crates/chronofork-megadrive/src/backend.rs:481-513`) is the *other* thing a reviewer
   must not remove — it is a view-construction fast path, not a second serializer. Landing
   both means one of them goes: **reuse the buffer and drop the ~18% micro-optimization**, and
   measure the net effect in W2-7. State that trade explicitly rather than keeping two paths.
2. **`clear()`, never `truncate` to a smaller end.** A stale tail would silently enter the
   digest. `clear()` plus the writer's own length decisions is the contract.
3. **`snapshot` copies out.** Handing the scratch buffer to a caller would alias it into a
   checkpoint; the payload is a fresh `Arc<Vec<u8>>` (see §7.2).
4. **No `unsafe`, and no `Rc`.** `RefCell` + an owned buffer keeps the workspace's
   no-`unsafe` rule and the `Backend: Send` bound. If a shared handle were ever genuinely
   needed, use `Arc<Mutex<..>>` and say why -- not `Rc`.
5. **Panic safety, stated correctly (R2b correction).** A panic while the `RefMut` is alive
   unwinds through the guard, whose `Drop` releases the borrow, so the cell is **not** left
   permanently borrowed and the machine is not poisoned the way a `Mutex` would be. The real
   residue is a torn buffer: `clear()` at entry means the next call overwrites it whole, so a
   partially written body is never hashed. No `catch_unwind` is added, and no panic is
   swallowed.

**The measured claim stays a hypothesis.** Reuse is expected to cut the ~116.6 µs/step
allocation/page-fault share of the observability path, and removing the hash from `step`
(W2-2) removes the body construction entirely from ordinary execution. Neither is an outcome
until W2-7 measures it; no fps number is claimed here.

**The real allocation win is still W2-2.** Once `step` stops hashing, ordinary execution builds
no body at all. Buffer reuse matters for the paths that *do* hash: verified runs, TAS replay,
snapshots and on-demand inspection.

### 7.2 `Arc` payload and `initial_state`

`BackendSnapshot.payload` becomes `Arc<Vec<u8>>` and `Session::initial_state` becomes
`Arc<BackendSnapshot>`. Byte equality is preserved: `Arc<T>::PartialEq` compares the
pointed-to values (ADR-0015 §6). `fork_current` currently materializes ~773.5–822 KiB per fork;
sharing removes the copies without touching the serialized format.

**No** `Arc::ptr_eq` anywhere in equality or hashing paths; if identity is ever needed it is a
new type, not a consequence of `Arc`.

**The pre-migration baseline is not a single-tree test (R2b).** Comparing two machines *after*
the change cannot prove the change preserved anything: an identical serialization defect in
both would pass. The requirement is therefore two-part, and only the first is a unit test:

1. **recorded values** -- `recorded_synthetic_digest_is_stable` (scaffold) and
   `state_hash_hashes_the_payload_state_body` (existing, `backend.rs`) pin the digest and the
   payload size so a serialization change fails a test;
2. **a cross-tree capture** -- for the real backend, the pre-change bytes are captured from the
   pre-migration tree (a `git archive` of the base plus the same harness), stored as an
   artifact, and compared after the change. This is a **procedure with a recorded artifact**,
   not a test that can exist in one tree. It is part of W2-7's evidence set, and its result is
   reported with the commit and tree digest it came from.

Claiming (1) as if it were (2) was the R2b finding; the spec now states both and labels which
one each artifact provides.

### 7.3 `reap()` — safe by construction

The requirement is "reap with an in-flight reader safe". A registry that hands out borrowed
`&mut` handles cannot satisfy it: removing the map entry while a caller holds a borrow is
rejected by the borrow checker, or becomes a lifetime problem the moment the handle crosses a
thread. Therefore:

```rust
/// Removes a closed session's entry from the registry.
///
/// Any handle already issued for that session stays **valid**: the handle owns a
/// count on the session's state, so completion of an in-flight operation cannot
/// observe a freed entry. New lookups by id fail with `UnknownSession`.
pub fn reap(&mut self, session: SessionId) -> Result<ReapOutcome, SessionError>;
```

Registry entries become `Arc<...>` and handles become owned clones. This makes `reap()`
correct **by construction** (no "check the refcount and hope"), at the cost of one `Arc` clone
per handle — which is what the registry already does implicitly through the manager lock. The
alternative (`reap` blocks until readers drain) is worse: it makes a maintenance operation
wait on an unbounded run, which contradicts the same rule that made cancellation lock-free.

`reap()` is **not** W3.3's quota accounting; W3.3 owns the closed-entry bound
(`max_closed_retained`, `closed_retention_ttl`) and the accounting contract. W2 provides the
safe removal primitive and the `Arc` sharing it needs.

## 9. D10 — TAS and versioning policy

### 9.1 `VerificationPolicy`

```rust
pub enum VerificationPolicy {
    /// TAS verification, precise divergence localization, debugging.
    EveryStep,
    /// Hash at 1-based multiples of `n`: steps 1, n+1, 2n+1, ...
    ///
    /// `n == 0` is accepted and means "never hash" rather than panicking: a policy
    /// is caller input, and a zero is a degenerate request, not a crash.
    EveryN(u32),
    /// Hash exactly the step whose **resulting** tick equals this value.
    ///
    /// One variant, not a `Checkpoints(Vec<Tick>)` list: the wire and the artifact
    /// envelope carry a single tick per run, and a list would be a second,
    /// unbounded grammar with no caller. If a caller ever needs several, it runs
    /// several batches.
    AtTick(Tick),
    /// Interactive inspection: a hash only when the caller asks.
    OnDemand,
    /// Ordinary execution: no per-step hash.
    None,
}
```

**This variant list is the only policy definition in the project (R2b-B).** An earlier revision
declared `EveryN(NonZeroU32)` and a separate `Checkpoints(Vec<Tick>)` in §9.1 while §4.5 used
`AtTick`, which is exactly the drift the reviewer caught: the two sections described different
types. `AtTick` and `EveryN` above are normative, `n` is a plain `u32`, and no `Vec` appears in
a policy.

1-based `EveryN` is normative: "every 5th step over 15 steps" is steps 1, 6 and 11, i.e.
**exactly 3** digests (the spec's scaffold and the harness probe both assert 3).

Defaults: `Session::step` = `None`; the service `run` = `OnDemand`; TAS record/play/verify and
the replay comparator = `EveryStep`. Only `EveryStep` and `EveryN` make a run use
`step_verified`; `AtTick` does so on the matching step only.

### 9.2 Movie policy

- **Existing movies (v1/v2)** replay through the verified path, unchanged. Their stored
  per-step digests are what verifies them; the reader must therefore use `step_verified`, not
  `step`.
- **New movies** declare the policy explicitly in the artifact envelope. The stored shape
  changes → the movie format version is bumped. Until the shape is actually finalized, store
  the policy in the envelope **without** bumping, and bump when the shape changes (ADR-0015
  §7 and open question 4: "yes if the stored shape changes").
- **First-divergence localization** is unchanged in principle: checkpoint + replay. The report
  names the first step whose digest differs from the movie's.
- **Never** silently accept a movie whose policy the reader cannot honour: a movie requesting
  `EveryStep` verification read by a build without the verified path must fail with a typed
  compatibility error, not fall back to `step`.

### 9.3 Artifacts carry their policy

Any artifact whose verification semantics changed (movie, experiment report, differential
golden) records the policy/version that produced it. This is the ADR's rule and it is also the
only way the golden re-record in §11.5 is auditable.

### 11.2 Why a **twin machine** and not "hash on demand equals hash on demand"

The tautological test — compute a hash, compute it again, compare — passes even if the ordinary
path executes differently from the verified path, because both call the same serializer on the
same state. The R1-C1/C8/V2-5 requirement is stronger: **drive one machine on each path with
the same inputs and compare their observable evolution**. If `step_verified` ever took a
different code path (a different interrupt boundary, an extra `sync_vdp_status`, a different
frame capture point), the ticks would diverge and the test fires. That is why the scaffold
compares `tick` and `halted`, not only digests, at **every** step.

The files are not split, and none of the four scaffold files is copied into `crates/` by this
task: adding files to a dirty shared worktree without coordination is what the ownership rules
forbid, and a partially-landed test file is worse than none. The integrator copies them whole at
the appropriate landing, or splits `w2_batch_semantics.rs` if the halves diverge.

**Landing seams this suite needs, listed explicitly (R2b-C).** The tests were written so that
nothing beyond this list is required, and in particular so that no speculative `Backend` method
had to be added: (1) `Backend::state_hash`, (2) `Backend::step_verified` +
`VerifiedStepOutcome`, (3) `Backend::status` + `MachineStatus` with the split register maps,
(4) `MachineInspection::memory` as an `Option`,
(5) `run_batch` + `StopBudget`/`StopSet`/`StopCondition`/`MatchedStop`/`StopReason`/`BatchOutcome`;
(6) `InputSequence` with `new`/`neutral`/`frame` and `MAX_INPUT_FRAMES`,
(7) `RunControl` with `new`/`with_deadline`/`cancel`/`is_cancelled`/`deadline`,
(8) `BackendSnapshot::{payload_arc, payload_allocation, payload_strong_count}`,
(9) `MAX_STATUS_REGISTERS`, (10) `BackendError::Limit { field, limit, requested }`.
Anything not on this list that a scaffold needs is a bug in the scaffold, not a missing API.

**R2c's correction is structural here.** The three readings a batch loop needs from its own
machine -- halt flag, tick, step cost -- are **not** on this list, because they are not part of
`Backend`. They live on `StubBridge`, the stub's own trait: a real backend reads its fields
directly inside its own `run_batch`. The landing adapter therefore implements exactly items
(1)–(10) and nothing else, and a compiled check enforces it:

```sh
python3 .research/implementation-2026-11-20/scaffold/harness/tools/check_adapter_contract.py <repo-root>
# adapter conformance: PASS (no E0407/E0046/E0599; CountingBackend: Send)
```

That probe takes the repository's **real** `Backend` body, adds exactly the four W2 additions,
and compiles the delivered adapter against it. Its negative controls reproduce R2c's findings:
declaring `is_halted` in the adapter gives `E0407`, omitting `write_memory` gives `E0046`.

### 11.5 Golden and evidence handling

- The step stops hashing at **W2-2**, so any golden that stored a per-step digest either
  re-records through the verified path or keeps asserting through it. No golden is deleted and
  none is weakened; a changed golden is explained by the policy change and re-recorded under
  the policy identifier from §9.3.
- The census is re-run at every landing and diffed against the digest recorded in that
  landing's commit; the baseline table in §1.3 (digest `26246f89…`) is the frozen reference, so
  a regression that re-adds a read is visible. Because the worktree is shared and moving
  (§1.5), a landing must record its own digest rather than assuming the live tree still matches
  the baseline.
- `./scripts/check.sh` plus the ADR-0015 block of the anti-slop workflow applies to every
  landing; the differential oracle is unaffected (it drives the emulator through the same
  public step path).

## 12. Open questions (for the owner / integrator, not for W2 to decide alone)

1. **Where does `step_verified`'s per-step hash get amortized?** The default calls
  `state_hash()` after `step`. A backend override may build the body once and both hash and
  snapshot from it. Recommendation: keep the default until W2-7 measures the verified path; do
  not optimize an unmeasured path (ADR-0015 notes the reviewed `step_verified` cost must be
  measured so the cost is not displaced onto TAS).
2. **`MachineInspection.memory` removal vs `Option`.** Recommendation: `Option` in W2, removed
  in the same 0.x break once consumers use `read_memory`. Keeps one migration instead of two.
3. **`MAX_STATUS_REGISTERS` value.** Recommendation: 64 (measured max ~44 today, headroom for
  8.5 controller/timer pseudo-registers), enforced by a test per backend.
4. **Movie version bump timing.** Recommendation: envelope-only until the shape changes
  (§9.2); the bump is a separate, named change.
5. **Does `status()` belong on `Backend` or only on `Session`?** Recommendation: `Backend`, so
  the debugger, trace and GUI reach it through the existing backend seam without a session
  round trip, matching where `inspect()` lives today.
